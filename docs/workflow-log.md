# AI Workflow Log

Why: to record how the Figma MCP + Elementor MCP + Claude Code stack actually works — what the agent does on its own,
where a human is needed and how long it takes. These notes later supply arguments for Upwork proposals
("here's how AI changed my process") and lessons for future projects.

## Takeaways (filled in as they accumulate)

- Before each stage, check the versions of external tools rather than relying on memory: in the three weeks after the MCP launch, Elementor shipped 5 patch versions (4.3.1–4.3.5), two of them with MCP fixes.
- Docker on Windows: don't mount WordPress from the Windows disk — keep core and plugins in a Docker volume and mount only the theme from the project. Measure a slow environment first (per-stage timing, file-read comparison), then pick a solution.
- The "latest version" of a plugin from WordPress.org is `latest-stable` or `wp plugin install`; the short `<slug>.zip` link may serve trunk (a pre-release).
- When connecting MCP to a client site: check the application password and the endpoint with `curl` before connecting the agent (a minute of work that rules out guesswork if something fails), add the server only in the project's local scope, don't paste the password into the chat, revoke it after the project.
- Elementor V4 via MCP: after creating classes, check whether properties ended up in `custom_css` (Free strips it silently). Verify the result with computed styles in the browser, not just the MCP response.
- Reviewing the foundation on a style guide (all tokens and classes on one page at 3 widths) catches errors before the first section and doubles as an artifact for the client and the portfolio.
- Check animations frame by frame: `document.getAnimations()` → pause → `currentTime` → screenshots. This shows what the eye can't catch in real time (in our case, a drop that didn't cover the screen). But if JS with timers is involved in the animation, pausing CSS doesn't stop them — recheck such places with a series of real-time screenshots.
- Supplement the self-check at the design width, 768 and 375 with intermediate widths (1025, 1180): breakages most often live between breakpoints. The Elementor editor canvas is narrower than the window, so it points to such places by itself.
- Consider an animation verified only when computed values change over time (several `getComputedStyle()` measurements), not when the element has an `animation-name`.
- After any global change (kit, menus, breakpoints), do a quick pass over all finished sections, not just the current one: that's how the unlinked header menu was found.
- A classic widget inside an atomic layout (form, menu): MCP doesn't create it, but a custom WP-CLI command using the Elementor document API handles it in a minute, and later MCP builds leave it alone. Such commands are worth keeping in the project — they'll come in handy on client sites.
- Data in UI kit designs can be real (company details, names) — proofread the copy before publishing, not just the layout.
- Count time from the session transcripts or commits instead of estimating it along the way: the agent's estimates in the table turned out about three times too high (H5: 45 minutes logged, 7 by the commits). Only counted numbers go to clients and the portfolio.

## Theme security review (2026-11-19)

Before linking the public repository from the Upwork portfolio, a separate agent reviewed the theme read-only: 2,359 lines of PHP, 663 lines of JS, the mu-plugin and the WP-CLI commands. Nothing critical. Two medium issues were confirmed, in the code and on the live demo:

- **Shortcodes from the search box.** `aiec_render_site_part()` ran `do_shortcode()` over every Site Part, the blog templates included, and the search query is printed in the title. `esc_html` leaves square brackets alone, so `/?s=[aiec_year]` showed "Search results for “2026”": any visitor could run any shortcode on the site. Fixed: shortcodes run only in the header and footer, where `[aiec_year]` lives.
- **Password-protected articles were shown in full:** the Post Content widget printed `the_content` without `post_password_required()`. It now shows the password form, and the template preview skips protected articles.
- **Low:** Authors could create Site Parts. They now use page capabilities (`capability_type => page`).
- **WordPress coding-standard details:** `esc_url` for `tel:` and `mailto:`, a server-side 1–12 limit for the Post Grid article count, `get_search_query( false )` instead of double escaping, `</` in the preview CSS.

**What didn't work.** A fallback — encoding `[` and `]` in the search title — had no effect: Elementor V4 re-parses the HTML of classic widgets inside atomic elements, and the entities turn back into brackets. It was reverted; the real protection is not running `do_shortcode()` on the blog templates.

**Checked locally:** searching `[aiec_year]` shows the text; the footer year is there in EN and DE; a temporary password-protected article shows the form and the template preview picks another article; Administrators and Editors can edit Site Parts, Authors can't; pages return 200 and `debug.log` has no new errors. The fix is live on the demo.

**Takeaway.** The agent-written code was careful (escaping at output, no `$_POST` or SQL at all), yet only a separate review found two real holes. Code from AI needs a security review before hand-over too.
